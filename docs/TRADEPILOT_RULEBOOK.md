# TradePilot AI — Engineering Rulebook\n\n**Version:** 1.0  \n**Effective:** 2026-09-29  \n**Repository:** varunaradhya/tradepilot-ai\n\n## 1. Purpose\nThis rulebook prevents duplicate work, undocumented changes, unsafe feature growth and false claims of readiness.\nThe repository itself is the source of truth.\n\n## 2. Mandatory first step before ANY feature work\nBefore creating or changing a feature:\n1. Read docs/TRADEPILOT_FEATURE_REGISTER.md.\n2. Read docs/TRADEPILOT_AUDIT.md.\n3. Search the repository for the existing capability.\n4. Search recent commits for previous implementations/fixes.\n5. Identify the existing service/API/component/test before writing new code.\n6. Decide one of:\n   - ALREADY IMPLEMENTED → do not recreate it.\n   - IMPLEMENTED BUT DEFECTIVE → fix the existing implementation.\n   - PARTIALLY IMPLEMENTED → extend the existing implementation.\n   - NOT IMPLEMENTED → add the minimum coherent implementation.\n   - ENVIRONMENTAL BLOCKER → document the blocker; never fake completion.\n\n## 3. No duplicate implementation rule\nNever create a second production engine, service, registry, validator, risk gate or data store when an existing implementation already serves that responsibility.\nIf two implementations already exist: compare responsibilities, identify the canonical implementation, migrate/reuse callers, remove or explicitly deprecate the duplicate, and update the register.\n\n## 4. Feature lifecycle\nDISCOVER → REGISTER CHECK → DESIGN/GAP ANALYSIS → IMPLEMENT OR FIX EXISTING → TEST → SECURITY/SAFETY REVIEW → CI → DOCUMENT → MARK COMPLETE\n\n## 5. Definition of Done\nA task can be marked DONE only when applicable:\n- Existing implementation was checked.\n- No unnecessary duplicate implementation was introduced.\n- Code is implemented.\n- Regression tests exist for important behavior/failure modes.\n- Backend tests pass when affected.\n- Frontend build/tests pass when affected.\n- Docker/deployment validation passes when affected.\n- Security and authorization implications were checked.\n- Trading safety boundaries were checked.\n- Documentation/register was updated.\n- Environmental dependencies are explicitly recorded.\n- No unsupported profitability/performance claim was introduced.\n- Git commit identifies the completed change.\nIf CI has not run or is not green, status must be IMPLEMENTED — CI PENDING, not DONE.\n\n## 6. Data honesty rule\nNever fabricate historical market data, broker responses, bid/ask evidence, paper-trading results, ML performance or CI results.\nNever treat synthetic fixtures as real-market evidence.\nSynthetic data may be used only for deterministic unit/contract tests and must be clearly labeled.\n\n## 7. Trading safety rules\n1. India/NSE first.\n2. Intraday first unless explicitly expanded.\n3. Paper/simulation first.\n4. Risk before execution.\n5. Evidence before promotion.\n6. No future leakage.\n7. No optimization against OOS data.\n8. Missing data fails closed where safety depends on it.\n9. Live order execution remains hard locked.\n10. No feature may bypass the central safety boundary.\n\n## 8. Research rules\nEvery research result must preserve dataset identity/version, symbol/instrument identity, interval, time range, strategy version, parameters, cost/slippage assumptions, data-quality status and experiment lineage.\nBacktest, walk-forward and OOS results must be reproducible from recorded inputs.\n\n## 9. Historical-data rules\nAll historical data entering research or paper validation must pass a shared contract covering Indian instrument identity, timezone, chronological ordering, duplicate timestamps, expected interval, OHLC validity, finite numeric values, volume validity, session/calendar validity, missing-bar/gap diagnostics and corporate-action treatment where applicable.\nA provider outage is not equivalent to an empty market result.\n\n## 10. ML rules\nML is an auxiliary research/paper layer, not permission to trade live.\n- Keep temporal ordering.\n- Keep training/validation/test separation.\n- Record feature schema and model version.\n- Record training sample count.\n- Record evaluation metrics.\n- Require separate trading-performance evidence.\n- Do not automatically promote based only on generic classification metrics.\n- Shadow mode is the default.\n- Paper ML requires explicit validated-model/data gates.\n- Live ML remains disabled.\n\n## 11. Database and migration rules\nAny new persistent model requires model definition, migration, metadata registration, initialization/import registration where applicable, regression tests, and upgrade verification.\nAlembic metadata must represent all persistent models.\n\n## 12. API rules\nEvery new endpoint must define authentication/authorization requirement, input validation, error behavior, idempotency where applicable, data-quality behavior, safety boundary, tests and response contract.\nNever silently swallow persistence or execution errors.\n\n## 13. Transaction rules\nRelated state changes that must remain consistent must share a transaction or have an explicit reconciliation mechanism.\nExamples: paper trade + learning event; validation day + validation symbols; experiment + dataset lineage.\n\n## 14. Frontend rules\nBefore adding a UI component, search for the existing page/panel/component; reuse existing API contracts; implement loading/error/empty/stale states; distinguish simulated/descriptive evidence from live capability; never display unsupported profitability claims; keep Indian-market scope consistent.\n\n## 15. Security rules\nNever commit broker secrets, JWT secrets, encryption keys, credentials or personal tokens.\nSecurity-sensitive functionality must fail closed.\n\n## 16. Documentation update rule\nWhenever a feature is added, fixed, materially changed, deprecated or intentionally locked, update the Feature Register and Audit when the finding/backlog changes, plus relevant architecture/runbook documentation.\n\n## 17. Completion ledger rule\nEvery completed task must have task ID, short description, implementation location, test/evidence, CI status, commit SHA, date and remaining limitations.\nDo not mark the same task as a new feature later. Reference its existing task ID and create a new defect/change ID when scope changes.\n\n## 18. New-feature decision rule\nQ1 Does it already exist? Yes → inspect it. No → design and implement.\nQ2 If it exists, is it correct? Yes → do not duplicate it; improve only for a concrete gap. No → fix it.\nQ3 Is there a test proving important behavior? Yes → extend if required. No → add one.\nQ4 Is it documented in the register? Yes → update status/change history. No → add it.\n\n## 19. Status vocabulary\n- DONE — CI VERIFIED\n- IMPLEMENTED — CI PENDING\n- PARTIAL\n- DEFECT FOUND\n- BLOCKED — ENVIRONMENT\n- PLANNED\n- LOCKED BY SAFETY POLICY\n- DEPRECATED\nDo not use vague statuses such as almost done or mostly complete.\n\n## 20. Current permanent locks\n- live broker order execution;\n- live ML deployment;\n- fabricated historical/bid-ask evidence;\n- unsupported strategy qualification;\n- automatic profitability claims.\n\n## 21. Rulebook maintenance\nIf a future workflow discovers a new class of duplicate-work or safety failure, add a rule here and update the register.\n\n**Golden rule:** CHECK FIRST → REUSE IF PRESENT → FIX IF BROKEN → ADD ONLY IF MISSING → TEST → VERIFY → DOCUMENT → REGISTER → COMMIT.\n
